## 1. Executive Summary

Phase F2.0.3 successfully transitions Nova AI from a regex-driven, static execution pipeline into a genuine, local-first, LLM-driven structured tool calling engine. 

Prior to this phase, Nova AI relied on regular expressions in `understand_task()` and hardcoded procedural sequences in `create_plan()` to trigger tool executions. In Phase F2.0.3, the local model (`qwen3:8b` via Ollama `/api/chat`) is directly empowered with standardized OpenAI/Ollama function calling schemas across all 19 real system tools registered in `UnifiedToolRegistry`. 

The model natively evaluates user prompts, reasons over tool availability, formulates structured tool calls with strongly typed arguments, receives verified execution outputs in multi-turn conversation context, and synthesizes natural-language answers with physical proof of execution. All tool operations remain strictly guarded by `WorkspaceSecurityGuard` (filesystem boundary containment) and `SecurityEngine` (permission classification and user confirmation gates).

## 3. Ollama Tool-Calling Wire Protocol & Schema Conformance

### 3.1 Request Wire Payload
When tools are enabled, `ProviderRouter` formats the request to `POST http://127.0.0.1:11434/api/chat`:
```json
{
  "model": "qwen3:8b",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "Inspect README.md and tell me what the repository name is."}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "read_document",
        "description": "Inspects and extracts real content...",
        "parameters": {
          "type": "object",
          "properties": {
            "file_path": {
              "type": "string",
              "description": "Path to file inside authorized workspace"
            }
          },
          "required": ["file_path"]
        }
      }
    }
  ],
  "stream": false
}
```

### 3.2 Response Parsing & Normalization
Ollama `/api/chat` returns:
```json
{
  "message": {
    "role": "assistant",
    "content": "",
    "thinking": "...",
    "tool_calls": [
      {
        "id": "call_tnekxvry",
        "function": {
          "name": "read_document",
          "arguments": {
            "file_path": "README.md"
          }
        }
      }
    ]
  }
}
```
`ProviderRouter` extracts and normalizes the payload:
- Coerces string-encoded JSON arguments into native Python dictionaries.
- Generates deterministic `id` values if omitted by older Ollama builds.
- Extracts Qwen3 thinking traces (`thinking` field) to maintain transparency.

### 3.3 Multi-Turn Tool Result Delivery
Tool execution outcomes are fed back to Ollama in the next conversational turn:
```json
{
  "role": "tool",
  "tool_call_id": "call_tnekxvry",
  "content": "{\"tool\": \"read_document\", \"success\": true, \"output\": {\"file_name\": \"README.md\", \"format\": \"MD\", \"line_count\": 120, ...}, \"verified\": true}"
}
```
The model processes the tool output in context and produces a final natural-language synthesis in Round 2.

## 4. Dynamic Tool Discovery & Registration Architecture

No tools are hardcoded in the model prompt or execution dispatcher. Instead:
1. `UnifiedToolRegistry` maintains the canonical registry of all 19 tools.
2. `UnifiedToolRegistry.get_tool_schemas()` exports OpenAPI/JSON Schema compatible definitions directly to the engine.
3. Supported tools span five functional categories:
   - **Math:** `calculate_math`
   - **Filesystem:** `read_document`, `create_file`, `file_operation`
   - **Desktop Automation:** `open_application`, `verify_application`, `close_application`, `list_windows`, `get_active_window`, `focus_window`, `close_window`, `keyboard_type`, `keyboard_press`, `keyboard_combination`, `mouse_move`, `mouse_click`, `capture_screenshot`
   - **Code Intelligence:** `analyze_code`
   - **System State:** `system_control`

## 5. Security & Permission Gating Implementation

Every tool call generated by the local LLM undergoes strict dual-layer security validation before any physical action is executed:

### 5.1 Layer 1: Filesystem Boundary Containment (`WorkspaceSecurityGuard`)
- Any parameter named `file_path`, `source_path`, `destination_path`, `path`, or `save_path` is evaluated via `guard.resolve_workspace_path()`.
- If the path targets an absolute or relative destination outside the authorized workspace (e.g. `C:\Windows\System32\...` or `..\..\secret.txt`):
  - Execution is immediately rejected with `WorkspaceSecurityException`.
  - A security event is recorded in the audit log.
  - The access denial is fed back into the conversational context so the LLM can explain the policy restriction to the user.
  - Zero disk I/O is permitted outside the workspace.

### 5.2 Layer 2: Permission Classification & User Confirmation (`SecurityEngine`)
- Tools classified as `ToolPermissionLevel.SENSITIVE` (e.g., `file_operation` delete/move, `close_window`, `keyboard_combination`, `mouse_click`) are checked against `SecurityEngine.check_approval_required()`.
- If approval is required and `is_user_approved=False`:
  - Physical execution is paused.
  - The invocation record is marked with `requires_approval=True`.
  - The loop status transitions to `NEEDS_APPROVAL`.
  - The LLM is informed of the approval hold and asks the user for explicit confirmation.

## 6. Execution Loop, Multi-Step Reasoning & Duplicate Call Prevention

`DynamicToolEngine.execute_tool_loop` enforces conservative operational constraints:

1. **Max Rounds Ceiling:** Bounded to `max_rounds=5` to prevent runaway recursive tool calls.
2. **Time Budget:** Hard timeout enforced via `time_budget_sec=60.0` based on `time.perf_counter()`.
3. **Duplicate Call Prevention Filter:** Computes a SHA-256 hash of `(tool_name, serialized_arguments)`. If an identical tool call is repeated within the same session without state change:
   - The duplicate call is blocked.
   - A warning message is returned to the model advising it to proceed with existing data.
4. **Natural Completion:** If the model outputs natural-language text with 0 tool calls, the loop terminates immediately and returns the answer.
5. **Final Summary Turn:** If the loop exhausts `max_rounds`, a final synthesis request without tools is sent to Ollama to summarize the completed actions.

## 7. Error Handling, Malformed Arguments & Edge Cases

| Scenario | Handling Mechanism | Outcome |
|---|---|---|
| Model generates unregistered tool name | Caught in `execute_tool_loop` via `registry.get(name)` | Tool result error fed to model: `"Tool '{name}' is not registered."` Model self-corrects in next round. |
| Model provides malformed/non-JSON arguments | Argument parsing handles stringified JSON, raw dicts, or scalar values | If invalid, returns structured error: `"Malformed arguments: expected JSON object."` |
| Tool execution raises physical exception | Caught in `UnifiedToolRegistry.execute_tool` | Encapsulated in `ToolExecutionResult(success=False, error=str(e))`. Delivered to model to explain or recover. |
| Ollama daemon unreachable or times out | Caught in `ProviderRouter.dispatch_request` with 15s connect / 120s read timeout | Clean `RuntimeError` explaining Ollama status. No unhandled crashes. |
| Conversational prompt without tool requirements | Model evaluates schemas and emits 0 `tool_calls` | Completes in 1 round with zero tool latency. |

## 10. Known Limitations & Ollama Version Constraints

1. **Ollama Minimum Version:** Function calling via `/api/chat` requires Ollama v0.3.0 or higher. The active version is v0.40.15, fully supporting tool calls.
2. **Thinking Latency:** `qwen3:8b` generates thinking tokens before outputting tool calls. On local GPU, reasoning takes 15–35 seconds per round depending on prompt complexity.
3. **Parallel Tool Calls:** Ollama currently dispatches tool calls sequentially in separate message objects or as a single list. The engine processes them in order with individual error handling.
